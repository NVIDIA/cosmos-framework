# Cosmos3-Nano INT8 g64 GEMM 真内核基准报告（H100 SXM 80GB）

日期：2026-09-13。数据来源：`int8_bench/results/bench_final.{json,md}`（400 行，20 个 case × 20 个内核）、`bench_recheck.{json,md}`（复测 42 行）、`tuned_configs.json`（120 条）、`probe_report.md`、`logs/test_kernels_run4.log`。本文所有数字均直接取自这些文件，未做任何外推；所有比值均为 GEMM-only 的 `t_baseline / t_kernel`（>1 = 更快），除非明确写"总时间"。

---

## 1. 一句话结论

**INT8 g64（SGLang 式 Triton 块缩放内核，per-token × per-channel × 64-K-group，目标数学精确复现）在 H100 上只有 166–363 TFLOPS，GEMM-only 为 bf16 cuBLAS 的 0.40–0.56×、官方 per-tensor FP8 的 0.21–0.35×（即慢 2.8–4.8×），与 handoff 第 5 节 "差距 10% 以内" 的目标相距甚远；瓶颈按大小依次是 Triton 块缩放内核的结构（BLOCK_K 被迫 ≤ 64 + 主循环内逐 K-tile 外积重缩放，g64→g128 就差 1.4–1.6×、Triton g128 对 DeepGEMM 同结构 FP8 g128 又差约 2×）、cuBLASLt INT8 IMMA 本身在这块卡上只到 838–975 TFLOPS（FP8 per-tensor 1300–1450），以及 INT8 必需的 int32→fp32 重缩放尾声（+6–23%）。** 同一硬件上 FP8 g128（DeepGEMM 1D2D）在 M ≥ 4096 时达到官方 per-tensor FP8 的 0.91–1.03×，说明"块缩放"本身不是障碍，缺的是 CUTLASS/DeepGEMM 级别的 INT8 块缩放内核，而且即便有，INT8 路径的上限也只是 per-tensor FP8 的约 0.6–0.75×。

## 2. 方法与环境

### 2.1 硬件与时钟
- 1× NVIDIA H100 80GB HBM3（节点 pool0-0977，Slurm job 7136301），132 SM，驱动 575.57.08 + CUDA 13.0 前向兼容 libcuda（580）。
- SM 最高时钟 1980 MHz，显存 2619 MHz，功耗上限 700 W。**时钟未锁定**（无 root；`Applications Clocks Setting: Not Active`）。在持续 GEMM 负载下观察到 SW power cap（throttle 0x4）：每个 case 2 s 预热循环后 SM 时钟落到 1155–1500 MHz（功耗 680–702 W），内核之间又回到 1980 MHz。每一行计时前都记录了 nvidia-smi 时钟（`clocks` 列）。
- 后果：bf16 基线在 case 末尾重测时漂移 +0.0%～+16.7%（20 个 case 中 11 个超过 3% 阈值，最差 12288×4096 M=1802 +16.7%，4096×4096 M=901 +11.3%）；FP8 rowwise 基线漂移 ≤ 6.1%。复测（bench_recheck，12 次基线重测）中 7 次漂移 2–6.5%，因此是系统性的。**报告中的比值均用 case 开头的基线时间；M ≤ 1802 时 5–10% 以内的差异应视为噪声。**

### 2.2 软件
- 容器 `imaginaire4_v12.1.0.sqsh`：python 3.12.3，torch 2.13.0a0+9186a08b2c.nv26.07（CUDA 13.3），triton 3.7.1，torchao 0.18.0，nvcc 13.3。
- cuBLAS 开关：`allow_bf16_reduced_precision_reduction=True`，`allow_tf32=True`，`preferred_blas_library=Cublas`，`CUBLASLT_WORKSPACE_SIZE` 未设。
- DeepGEMM：commit 66081d4（2026-09-10 "Public Release 26/09"），在 `int8_bench/third_party/DeepGEMM` 树内编译（`TORCH_CUDA_ARCH_LIST=9.0a`），JIT 缓存 `third_party/dg_cache`，`deepgemm_verify.py` 全部 PASS。状态：**可用**。
- SGLang 内核源码：本地 clone @22e4b3a 的 `_w8a8_block_int8_matmul` / `_w8a8_block_fp8_matmul` / `per_token_group_quant_*`，复制到 `int8_bench/kernels/block_kernels.py`（未修改数学）。

### 2.3 GEMM、形状与 M
- `Y[M,N] = A[M,K] @ W[N,K]^T`，A 行主序激活，W 为 nn.Linear 权重 `[N,K]` 行主序，bf16 输出。
- 形状 (N,K)：(4096,4096) q/o_proj；(1024,4096) k/v_proj；(12288,4096) gate/up_proj；(4096,12288) down_proj。
- M：901（t2i 单分支）、1802（cond+uncond）、4096、16384、42240（t2v 720p×189 帧）。共 20 个 case。

### 2.4 计时方法
- **主指标**：`triton.testing.do_bench(warmup=25 ms, rep=100 ms, return_mode="median")`，每次重复前把 256 MB 缓冲清零以冲掉 50 MB L2（cold-L2），对 cuBLAS / cuBLASLt / DeepGEMM / Triton 完全相同。cold-L2 中位数偏保守：生产中 A 刚被写出（L2 热），只有 W 是冷的，小 M 时会压缩内核之间的差异。
- M ≤ 1802 另给 `do_bench_cudagraph` 中位数（warm-L2，无 launch 间隙，`warm us` 列）。
- 每个 case 开头 2 s bf16 GEMM 预热循环；case 末尾重测 bf16 与 FP8 rowwise 基线，>3% 漂移打旗。
- 激活量化单独计时（`act-quant us`）：融合 Triton 量化器（一次读 bf16、一次写 int8/fp8 + scale）；ModelOpt 静态 scale 路径只计 cast。`total = GEMM + act-quant`。权重量化离线，不计时。eager torch 量化器（int8_speed.py 风格，约 9 个未融合 pass）单列，不进 total。
- TFLOPS = 2·M·N·K / t（INT8 路径同口径记作 TFLOPS 即 TOPS）。

### 2.5 精确性检查（全部通过）
- 参考：每个内核**自己的量化操作数**（同一 qa/qw/scale）在 fp64 下的精确结果；INT8 主循环是 int32 精确点积，各组 fp32 累加，bf16 输出——与 `cosmos_framework/utils/generator/quantization.py::fake_quant_int8` 的定义一致（对称 INT8、qmax 127、rint 四舍六入五成双、scale = 组 absmax/127（fp32））。
- 通过线：rel-L2 < 3e-3（bf16 输出取整地板 ≈ 1.65–1.66e-3，fp32 累加再加 ~1e-6）；`int8_int_mm_raw` 为 int32 输出，要求逐位相等（rel-L2 = 0）；使用 `use_fast_accum=True` 的两条官方 FP8 路径放宽到 1e-2（Hopper 快速累加是有意的精度损失）。
- 验证在真实 M 上做：M ≤ 4096 全部行；更大 M 取 1024 + (M % 4) 行（走到 M%4 填充路径）。**bench_final 的 400 行全部 verify_ok**：非 fast-accum 内核 rel-L2 1.65e-3～1.70e-3（即 bf16 地板），fast-accum 的 `fp8_rowwise` / `fp8_pertensor_modelopt` 2.02e-3～3.89e-3（K=12288 时更差）；`int8_int_mm_raw` 全部 0.00e+00。
- 激活量化器逐位精确：13 个量化器（int8/fp8 g64/g128、per-token、per-tensor、k-major / TMA 对齐 scale 布局）对参考量化器 q 与 scale 均 0 mismatch（M=901,K=4096 共 3,690,496 元素）；融合 int32 重缩放尾声与 eager 版逐位相等。
- cuBLASLt 1×128 块缩放 FP8 的 fp32 输出 rel-L2 1.27e-4 = per-tensor FP8 fp32 输出的 1.28e-4，说明 cuBLASLt 按目标数学（g128）精确施加组 scale。
- 调参数值过滤：`tune.py` 每个候选配置对默认配置输出要求 rel-L2 < 1e-3。3 个 fp8_g128_bn128 case 共 264 个 BLOCK_K=64 子块配置因 rel-L2 1.02–1.18e-3（fp32 求和顺序不同导致 bf16 取整翻转）被拒；这是过滤器保守，不是错误，三例最终都选到了 BLOCK_K=128 配置并在 bench 中对 fp64 复核 PASS。120 个 case 无 OutOfResources / 编译失败。

### 2.6 调参
- `tune.py`：每个 (family, N, K, M) 扫 BLOCK_M∈{64,128,256(+32 小 M)} × BLOCK_N∈{64,128,256} × BLOCK_K∈{32,64}(g64) / {64,128}(g128) × warps{4,8} × stages{3,4,5} × GROUP_M{8,32(+64 大 M)}，剪枝后 116–132（M ≤ 4096）/ 174–198（M ≥ 16384）个配置全部计时（do_bench 中位数）。6 个族 × 20 case = 120 条，共 50.2 min（37.9 + 12.3）。
- 结果：g64 族 40 例中 39 例选了 `64×128×64 w4 s3–5`（仅 1 例 64×64×64），g128 族选 `64×128×128 w4`（fp8 g128 有 3 例 64×256×128 w8，int8 g128 bn1 有 1 例 64×64×128）。128×128 及以上 tile、8 warps 几乎从未获胜，即上限来自内核设计而非配置。
- `bf16_triton`（校准内核）未在调参名单里，使用内置默认 128×256×64 w8 s3，标记 UNTUNED；没有任何比值依赖它。

## 4. 观察

### 4.1 Triton 对 cuBLAS 的校准差距（bf16_triton）
- 默认配置的 Triton bf16 wgmma 内核在 M ≥ 4096 时达到 cuBLAS 的 0.90–0.99×（646–697 对 665–737 TFLOPS）；N ≥ 4096 且 M ≤ 1802 时 0.85–0.90×；只有 N=1024 小 M 掉到 0.47×/0.66×（128×256 tile 在 N=1024 上只有 4 个 N-tile，132 个 SM 填不满）。
- 结论：Triton 3.7.1 在 sm_90a 上的 wgmma 代码生成本身对 cuBLAS 只差 ≤ 10%，INT8 块缩放内核 0.40–0.56× 的差距是内核结构造成的，不是 Triton。

### 4.2 g64 相对 g128 的代价
- 固定 W 粒度只改组大小：`g64_bn1 / g128_bn1` 时间比 1.37–1.51×，`g64_bn128 / g128_bn128` 1.49–1.60×。
- 原因：SGLang 内核每个 K-tile 载入一对 scale 并按 `k_start // group_k` 索引，要求 `BLOCK_SIZE_K ≤ group_k`，所以 g64 被迫 BLOCK_K=64：每个流水级的 MMA 工作量减半、K 循环次数翻倍、`acc += dot(a,b).to(f32) * a_s[:,None] * b_s[None,:]` 这个 64×128 fp32 外积重缩放的次数翻倍。调参器扫过的 BLOCK_K=32 从未获胜。
- 调研（survey 3.1）预期 g64 比 g128 多 5–15%，**实测 37–60%**。
- Triton g64 INT8 最好 363 TFLOPS，g128 INT8 最好 646 TFLOPS（4096×4096 M=42240）。

### 4.3 block_n=1（per-channel W）相对 block_n=128 的代价
- `g64_bn1 / g64_bn128` 1.12–1.19×；`g128_bn1 / g128_bn128` 1.17–1.32×。per-channel 时每个 tile 要载入 BLOCK_N 个 W scale 并做外积，bn128 时只是一个标量乘一个向量。
- cuBLASLt FP8 双胞胎给出同样的方向：1×128/1×128 对 1×128/128×128 慢 1.16–1.33×（M ≥ 4096），852–961 对 1048–1176 TFLOPS。
- DeepGEMM 1D1D（W per-channel）对 1D2D 慢 1.47–2.17×，但这是 fp32 输出 + 单独 cast 的公平性问题，不能直接当作 per-channel 的内核代价。
- 含义：若精度允许，把 W scale 从 per-channel×64 改成 128×64 块可白拿 12–19%（Triton 实测）。

### 4.4 激活量化开销
- 融合 Triton INT8 g64 量化器：K=4096 时 M=901/1802/4096/16384/42240 分别 10.7–11.3 / 15.1 / 25.6–25.7 / 80.4–81.5 / 192–194 us；K=12288 时 19.2 / 31.7 / 62.8 / 224 / 563 us。M=42240 时有效带宽 2.7–2.8 TB/s（读 bf16 + 写 int8 + scale），即 HBM3 带宽约束；M=901 只有 ~1.0 TB/s（launch 约束）。
- g64 / g128 / per-token / FP8 静态 cast 的量化器时间几乎相同（M=42240,K=4096：194 / 192 / 201 / 177 us），组 absmax 归约不额外花钱，**各路径之间的差异全在 GEMM**。
- 占比：对 N ≥ 4096 形状，量化占 INT8 g64 GEMM 的 2–6%、占 `_int_mm` raw 的 4–25%、占 FP8 per-tensor GEMM 的 6–41%；对 N=1024（k/v_proj）量化本身就与 FP8 GEMM 同量级（占 75–85%）。总时间上，`_int_mm`+融合尾声+量化 对 bf16 为 0.54–1.17×，对 FP8 rowwise 总时间 0.53–0.80×。
- eager torch 量化器（int8_speed.py 风格）85–9528 us，是融合版的 7–17×（M=901 85.2 对 11.3 us；M=42240 3226 对 194 us）。**生产必须用融合量化器**（Triton 或 torch.compile），否则任何 GEMM 收益都会被抹掉。动态 per-tensor FP8 量化（amax 归约 + cast 两个内核）16.5–850 us，是融合 per-row 的 1.5–1.65×。

### 4.5 wgmma 与否（探针结论）
- probe 第 4 节：Triton 3.7.1 在 sm_90a 上把 int8 `tl.dot` 编译成 `wgmma.mma_async.sync.aligned.m64n128k32.s32.s8.s8`（SASS `IGMMA.64x128x32.S8.S8`），`mma.sync` 计数为 0；对 BM 64/128、BK 64/128、4/8 warps、M=901 掩码情况都成立。fp8 走 `QGMMA.64x128x32.F32.E4M3.E4M3`，bf16 走 `HGMMA.64x128x16`。
- 朴素 Triton int8 128×128×128 w8（无 scale）在 4096³ 上到 1061 TOPS（指示性），高于 cuBLASLt `_int_mm` 的 794–894 TOPS。**INT8 tensor core 指令不是瓶颈，块缩放内核的结构才是。**
- B 布局决定性：权重必须保持 `[N,K]` 行主序并以 `W.t()` 步幅索引（K-major smem tile）；给 `[K,N]` 行主序 B 时 int8/fp8 慢约 5×（bf16 不受影响）。`torch._int_mm` 同理：`W.t()` 视图 794 TOPS，`W.t().contiguous()` 125 TOPS（int8_speed.py 原样即为此慢路径：本基准 94–126 TFLOPS，0.13–0.18× bf16）。
- 同布局 FP8 与 INT8 Triton 内核时间比 0.93–1.07×（g64 0.96–1.02×），进一步说明数据类型无关，是内核结构决定成本。

### 4.6 小 M 与大 M
- M=901（7.6–90 GFLOP）cold-L2：bf16 cuBLAS 本身只有 354–724 TFLOPS；`_int_mm` raw 0.93–1.13× bf16，warm-L2（cudagraph）1.13–1.33×；FP8 per-tensor cold 1.50–1.95×、warm 1.87–1.93×。cold-L2 冲刷加上 launch 开销在小 M 压平了差异，warm-L2 列是小 M 更公平的指标。
- M ≥ 4096 时各路径饱和：INT8 Triton g64 323–363，g128 553–646，`_int_mm` raw 756–975，cuBLASLt FP8 1×128/128×128 1048–1176，DeepGEMM FP8 g128 1029–1412，FP8 per-tensor 1137–1407，FP8 rowwise 1148–1447 TFLOPS。
- Triton g64 的 TFLOPS 从 M=901 的 166–309 升到 M ≥ 4096 的 323–363 后就平了，与 M 无关，是计算侧上限。

### 4.7 异常与注意事项
1. **cuBLASLt INT8 只有 bf16 的 1.2–1.4×**：`int8_int_mm_raw` 大 M 时 838–975 TFLOPS（bf16 665–737），而非预期的 1.5–2×；FP8 per-tensor（1.63–2.00×）和 rowwise（1.64–2.04×）都在预期带内。复测复现（855–907 TFLOPS，1.23–1.31×）。计时前 nvidia-smi 采样：`_int_mm` 行 SM 时钟 1230–1980 MHz、功耗 400–702 W、throttle 0x4（bf16 行采样时 1980 MHz，FP8 per-tensor 行 1185–1980 MHz），即 INT8 IMMA 内核撞功耗墙更狠，加上 cuBLASLt SM90 int8 内核效率本身不高。加上必需的重缩放尾声（`fused/raw` 1.06–1.23×）后 INT8 per-token/per-channel 路径 GEMM-only 为 bf16 的 0.78–1.33×、FP8 per-tensor 的 0.48–0.68×。
2. **基线漂移**（见 2.1）：11/20 case 打旗，bf16 末尾重测 +2.3%～+16.7%。
3. **SGLang 式 Triton INT8 g64 在本栈上就是慢**：bn1 357–368 TFLOPS（大 M）、bn128 413–427；g128 变体 bn1 495–531、bn128 617–646；复测在 1% 内复现。是测量结论，不是错误。
4. **调参数值过滤器拒掉 264 个配置**（3 个 fp8_g128_bn128 case，BLOCK_K=64 子块，rel-L2 1.02–1.18e-3 对默认输出）——保守但无害，最终配置均经 fp64 复核。
5. **`_int_mm` 小 M 无加速**（cold 0.93–1.13×，warm 1.13–1.33×）：符合 launch + 冷 L2 主导。
6. **bf16_triton 20 行为默认配置（UNTUNED）**：仅作校准，无比值依赖它。
7. cuBLASLt 块缩放 FP8 要求 M % 4 == 0（901、1802 需零填充到 904、1804 再切片），且不支持 fast_accum；`ScalingType` 无 1×64 成员，**cuBLASLt 没有任何 g64 路径（INT8 或 FP8）**。`torch._int_mm` 要求 M > 16、K,N % 8 == 0。

## 5. 对 handoff 第 5 节问题的回答

**问：INT8 g64 与 per-tensor FP8 的差距是否在 10% 以内？**
**答：不在。差距是 2.8–4.8×（GEMM-only），而且现有一切 INT8 路径都做不到。**

| 比较对象（GEMM-only 除非注明） | 对 FP8 per-tensor(官方) | 对 bf16 cuBLAS | 对 FP8 rowwise(生产默认) |
|---|---|---|---|
| Triton INT8 g64 bn1（目标数学） | **0.21–0.35×**（M ≥ 4096：0.25–0.28×，即慢 3.5–4.0×） | 0.40–0.56× | 0.25–0.39× |
| 同上，GEMM + 激活量化总时间 | 慢 2.06–3.98× | 0.37–0.52× | — |
| Triton INT8 g128 bn128（放宽到组 128 + W 块 128） | 0.40–0.59× | 0.75–0.96× | 0.35–0.56× |
| cuBLASLt `_int_mm` + 融合重缩放（per-token/per-channel，放弃 K 分组） | 0.48–0.68× | 0.78–1.33× | 0.50–0.79× |
| cuBLASLt `_int_mm` raw（无 scale，INT8 的下界） | 0.58–0.73× | 0.93–1.42× | 0.61–0.86× |
| 对照：DeepGEMM FP8 g128（1×128 / 128×128） | 0.71–1.03×（M ≥ 4096：0.91–1.03×） | 1.06–1.96× | 0.89–1.21× |
| 对照：cuBLASLt FP8 1×128/1×128（目标布局 g128 FP8） | 0.52–0.84× | 0.94–1.39× | 0.66–1.05× |

**瓶颈（按贡献排序）**
1. **内核结构（最大项，约 2–3.5×）**：SGLang 块缩放内核在主循环里每个 K-tile 做一次 `int32→fp32 + 外积重缩放`，并要求 BLOCK_K ≤ 组大小。g64→g128 差 1.4–1.6×（4.2），bn1→bn128 差 1.1–1.3×（4.3），而 Triton g128 bn128 本身也只有 bf16 的 0.75–0.96×，对比结构相同的 DeepGEMM FP8 1D2D 达到 bf16 的 1.47–1.96×——同样的缩放结构，手写（TMA + warp 特化 + 组末提升）比 Triton 直译快约 2×。调参空间里 128×128 tile / 8 warps 从未获胜，配置层面已无油水。
2. **这块 H100 上 cuBLASLt INT8 的实际速率只有 838–975 TFLOPS**（规格 INT8 = FP8 = 1979 dense），而 FP8 per-tensor 1300–1450。handoff 第 1 节"GEMM 部分与官方 per-tensor FP8 同一 MMA 速率"的前提在实测中不成立：厂商库 INT8 只到 FP8 的 0.58–0.73×，且撞功耗墙时钟落到 1230–1755 MHz。朴素 Triton IGMMA 曾到 1061 TOPS（指示性），所以真实上限可能略高于 cuBLASLt，但没有证据表明能到 1.3 PTOPS。
3. **INT8 的重缩放尾声不是免费的**：FP8 cuBLASLt/DeepGEMM 在内核内施加 scale，INT8 `_int_mm` 只能出 int32，再融合一遍 `× s_a × s_w → bf16` 要多花 6–23%（4096×4096 M=42240：1691 → 1985 us，多 294 us）。
4. 激活量化对两边一样（4.4），不是 INT8 特有的劣势；但因为 INT8 GEMM 更慢，总时间比值略好于 GEMM-only 比值。

推论：即使写出 DeepGEMM 级别的 INT8 g64 内核，其上限也被第 2 项钉在 per-tensor FP8 的约 0.6–0.75×；"10% 以内"在 H100 上不可达。要不要继续 INT8 g64，取决于 handoff 第 1 节的精度收益（t2i PSNR 26.2 dB 对官方 FP8 17.8 dB）是否值得 GEMM 慢 1.3–1.7×（相对 FP8）但仍比 bf16 快 1.1–1.3×（大 M，见第 6 节 C 的估计）。

## 6. 下一步建议（预期收益以实测数为基准）

**A. 先测 INT8 的真实上限（0.5 人日，决策门）**
用 CUTLASS 3.x SM90 INT8 wgmma per-tensor GEMM（无 scale）或探针里的朴素 Triton 128×128×128 w8 内核跑 4 个形状 × 5 个 M，最好能请管理员临时锁时钟（`nvidia-smi -lgc 1980`，需 root）。已知参考：cuBLASLt `_int_mm` 838–975 TFLOPS，朴素 Triton IGMMA 4096³ 1061 TOPS（指示性）。若上限 ≈ 1.0–1.1 PTOPS，则 INT8 g64 的最好情形 ≈ FP8 per-tensor 的 0.65–0.75×，应据此决定是否投入 C/D。

**B. 展开 K 的 Triton 变体（1–2 人日，低风险）**
在 `kernels/block_kernels.py` 的 int8 内核中把 BLOCK_K 提到 128/256，每 64-K 子块单独 `tl.dot` 得 int32 子累加器，同一 tile 内各子块转 fp32 后各乘自己的 scale 再相加，使流水级工作量与 g128 相同；同时把 bn1 的 W scale 载入改成向量一次性预取。**预期**：把 g64 提到目前 g128 bn128 的水平——M ≥ 4096 时 553–646 TFLOPS，即比现在的 g64（323–363）快 1.7–1.9×，达到 bf16 的 0.79–0.96×、FP8 per-tensor 的 0.45–0.50×。上限就是 Triton 这类"主循环内重缩放"结构的上限（≈ 650 TFLOPS），不会更多。

**C. DeepGEMM SM90 1D2D 移植到 INT8 + BLOCK_K=64（2–3 人周，survey 路径 4）**
本容器中 DeepGEMM 已编译、已验证（`third_party/DeepGEMM`，`deepgemm_verify.py` PASS），FP8 1D2D 实测 1029–1412 TFLOPS = 官方 per-tensor FP8 的 0.91–1.03×（M ≥ 4096）、cuBLASLt FP8 per-tensor 速率的 87–97%。若同样的效率转移到 INT8，**预期 ≈ 0.9 × (838–975) ≈ 750–880 TFLOPS**：比当前 Triton g64 快 2.1–2.4×，为 bf16 的 1.1–1.3×，但仍只有 FP8 per-tensor 的 0.55–0.65×。改动点：放宽 `sm90_fp8_gemm_1d2d.cuh` 的 FP8 断言、`heuristics/sm90.hpp` block_k=64、smem swizzle 64B、SFA/SFB TMA 描述符按 K/64、新增 S8 wgmma selector、int32→fp32 后 `final_accum += sa*sb*accum`（g64 使提升次数翻倍）。W 建议用 128×64 块（bn128）：DeepGEMM 的 per-channel W 只有 1D1D（fp32 输出 + cast，慢 1.47–2.17×），且 Triton 实测 bn1 比 bn128 慢 1.12–1.19×。`kernels/deepgemm_wrapper.py` 与 TMA 对齐的 scale 量化器（`actq_fp8_g128_triton_dg`）可直接复用。

**D. CUTLASS SM90 blockwise collective INT8 移植（2–3 人周，survey 路径 3）**
预期水平与 C 相同（CUTLASS blockwise FP8 与 DeepGEMM 同量级）。因 C 在本环境已有可运行的 FP8 对照与工具链，优先 C；D 的价值在于不依赖 DeepGEMM JIT 框架、便于进 cosmos-framework 的 CUDA 扩展。

**E. 不写内核的替代：FP8 g128**
DeepGEMM FP8（A 1×128，W 128×128）M ≥ 4096 时 = FP8 per-tensor 的 0.91–1.03×（M ≤ 1802 0.71–0.95×）；cuBLASLt `F.scaled_mm` 1×128/128×128 0.81–0.92×（M ≥ 4096；需 M%4==0 填充）。这是今天就能用的"细粒度缩放"路径，但它是 FP8 不是 INT8，且 handoff 第 6 节记录 FP8 模拟 g64 比 per-row 还差、原因未查——需先在模拟器里重做 FP8 g128 精度验证。

**F. 无论哪条路**：生产接入必须用融合激活量化器（4.4：eager 版慢 7–17×）；`_int_mm` 路径权重必须保持 `[N,K]` 行主序并传 `W.t()` 视图（否则慢约 6×）；对 M ≤ 1802 的形状用 CUDA graph（warm-L2 列比 cold 列好 10–35%）。
