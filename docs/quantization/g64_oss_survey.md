# 开源生态中 "g64" 双操作数 K-group 缩放 8-bit GEMM 调研报告

日期: 2026-09-12  作者: pzeren (由 Claude 汇总)
目标算子: `Y[M,N] = A[M,K] @ W[N,K]^T`，A/W 均为 8-bit，activation scale `s_a[m, k//64]`（per-token, dynamic），weight scale `s_w[n, k//64]`（per-channel, static），scale 沿 reduction 维变化，必须在 K loop 内逐 K-tile 应用（category A）。INT8 优先；GB300/Rubin 无 INT8 tensor core，需要同 scale 结构的 FP8 孪生版本。可接受的退化: group-128（DeepSeek 1x128 / 128x128）与 per-token/per-channel epilogue 缩放。

分类定义: (A) 双操作数 K-group scale 在 mainloop 内应用; (B) 仅 weight 有 group scale（MMA 前反量化到 activation dtype）; (C) per-token/per-channel scale 在 epilogue 应用; (D) 硬件 block-scaled MMA（MXFP8/NVFP4, e8m0/e4m3 micro-scale, Blackwell 专用，不可移植）; (E) 不支持。
g64 状态: native（现成）/ config-only（改配置或参数即可）/ code-change（需要改 kernel 代码）/ impossible（结构上不可行或需要重写）。

调研对象（均为 2026-09-10 ~ 09-12 的 main 分支，路径见附录）: vLLM, SGLang(+sgl-kernel), DeepGEMM, CUTLASS(3.x + CuTe DSL + 2.x), TensorRT-LLM, FlashInfer, lmdeploy, lightllm, torchao, llama.cpp(ggml-cuda), Atom, omniserve(QServe), marlin, bitsandbytes, ModelOpt, oneDNN。所有 file:line 均在本地 clone 上用 grep 复核过（本报告第 2 节标注 "已复核"）；只来自子调研、未在本机重新打开文件的条目标注 "unverified"。

## 1. 结论（一段话）

**今天没有任何开源栈交付 category-(A) 的 INT8 group-64 GEMM kernel。** 最接近的现成实现是 SGLang 的 Triton `_w8a8_block_int8_matmul`（`python/sglang/kernels/ops/quantization/int8_kernel.py:276-280`）：int8 x int8 `tl.dot` -> int32 -> fp32，再乘 `a_s[:,None]*b_s[None,:]`，scale 按 `k_start // group_k` 索引，`block_size=[n,64]` 即可算出精确的 g64 收缩（此前已数值验证），但这是 Triton 通用 kernel，没有任何 g64 的 tuned config，也没有 CUTLASS/DeepGEMM/cuBLAS 级别的 INT8 实现。**INT8 group-128** 同样只有 Triton（SGLang dense + MoE；vLLM 仅剩 MoE kernel 且未接线，dense 的 `w8a8_block_int8_matmul` 已在 2026-07/08 作为 dead code 删除）。**FP8** 情况好得多：group-128 是生态标准（DeepGEMM、CUTLASS SM90/SM100/SM120 blockwise、vLLM/SGLang/TRT-LLM/FlashInfer 的 CUTLASS 封装、torch._scaled_mm/cuBLASLt on SM90），全部 hardwire 1x128/128x128；FP8 **group-64** 在 Blackwell 上由 CUTLASS SM100 blockwise collective 原生支持（`sm100_mma_warpspecialized_blockwise_scaling.hpp:140-145` 只要求 GranK % 32 == 0 且整除 TileK，单元测试覆盖 64x64x64 与 64x4x32），fp32 scale、非 MX 指令、sm_103a(GB300) 可编译，但没有任何上层框架把 64 暴露出来（FlashInfer/vLLM/SGLang 的 dispatch 都写死 128）；在 Hopper 上 FP8 g64 只能走 Triton（vLLM/SGLang 的 dense block kernel 为 config-only；lmdeploy 亦 config-only 但要求 W 块 n>=128 且 group_ak==group_bk、不能表达 per-channel W；lightllm 的 `fp8w8a8g64` 只有激活侧 K-group，W 侧 per-channel scale 在 K loop 外一次加载，要成为双操作数 g64 需改 ~2 行）或改 CUTLASS SM90 collective（`ScalePromotionInterval % 4` 断言）。此外 llama.cpp 的 Q8_0 x Q8_1 MMQ 路径多年来一直在做 category-A 的 INT8 双操作数 K-group 缩放，但 group 固定为 32（格式内建），不是 server-class GEMM。

## 4. 生态系统实际在做什么，以及为什么

1. **per-token / per-channel INT8（SmoothQuant 血统, category C）**: vLLM `CutlassInt8ScaledMMLinearKernel`、sgl-kernel `int8_scaled_mm`、TRT-LLM `int8_gemm`（`EpilogueVisitorPerRowPerCol`）、lmdeploy W8A8、omniserve W8A8、torchao `Int8DynamicActivationInt8Weight`（"Only PerTensor and PerRow are supported"）、bitsandbytes LLM.int8、ModelOpt `INT8_DEFAULT_CFG`（per-channel W + per-tensor A）。原因: INT8 tensor core 在 K 上做 int32 精确累加，scale 只在 epilogue 乘一次，零成本；cuBLASLt 对 INT8 根本没有 scale mode，硬件也没有 per-K-group 的 INT8 缩放语义，所以任何 K-group 方案都得自己写 mainloop。生态的判断是: 用 SmoothQuant/旋转把 outlier 问题推到离线侧，比在 kernel 里做 K-group 缩放划算。SM100/SM120 上 vLLM/sgl-kernel 干脆不编 INT8（"Use FP8 quantization instead"）。
2. **weight-only group scale（W4A16 / W4A8 / W8A16, category B）**: Marlin、TRT-LLM `fpA_intB_gemm`（group 64/128；fp8 激活时只允许 128）、QServe（G=128, 两级 int4->int8->int32）、torchao Intx `PerGroup(32)`、CUTLASS mixed-input、ModelOpt `FP8_2D_BLOCKWISE_WEIGHT_ONLY`。原因: decode 是 memory-bound，只压权重即可拿到收益；激活保持 16-bit 或 per-token 8-bit，无需 K-group，反量化在寄存器里完成，MMA 仍是标准指令。
3. **DeepSeek 1x128 / 128x128 FP8（category A, group 128）**: DeepGEMM 发明的 "promotion" 技巧（临时 fp32 累加器 + 每 BLOCK_K 一次 FFMA 折入主累加器）被 CUTLASS SM90/SM100/SM120 blockwise collective、TRT-LLM `fp8_blockscale_gemm`、FlashInfer、vLLM、SGLang 全部复制。128 不是巧合: 它等于 TileK，且 wgmma K=32 时恰好 4 条 MMA 一次 promotion（CUTLASS 直接把 `ScalePromotionInterval % 4 == 0` 写成 static_assert，DeepGEMM 写 `BLOCK_K == 128`），promotion 的 FFMA 开销被摊到最小；同时 128x128 权重块可以由 TMA 一次搬运。因此 128 被 hardwire 进了 8 个以上的代码库，g64 在 Hopper 上没有现成品。
4. **MX / NVFP4 硬件块缩放（category D）**: Blackwell tcgen05 `kind::MXF8F6F4` 提供免费的 per-32 UE8M0 缩放，DeepGEMM 的 SM100 路径、TRT-LLM trtllm-gen MoE、FlashInfer/sgl-kernel MXFP8 ES MoE 全部改用它；这解释了为什么没人在 Blackwell 上投入软件 g64: 硬件已经给了 g32，代价是 scale 只能是 2 的幂且不可移植到 Hopper/Ampere/Thor。
5. **真正做 INT8 双操作数 K-group 的只有 llama.cpp（group 32）和研究代码 Atom（INT4 group 128）**: llama.cpp 的 Q8_0 x Q8_1 MMQ 在每 32 元素块上做 dp4a/mma.sync int32 点积再乘 `dA*dB`（fp16 scale），已在消费级 GPU 上运行多年，证明 "K-group INT8 + fp32 折入" 在 mma.sync 级别是可行的，但它不是 TMA/wgmma/tcgen05 结构，group 是格式内建的 32，也无 server-class 对比数据；Atom 用 `mma.m16n8k64.s4` 每 128-K 群组乘 half2 scale 折入 float，注释里预留了 "INT8 -> BLOCK_K 64" 但没有实现。
6. **激活侧量化 kernel 不是瓶颈**: vLLM/SGLang/lmdeploy/lightllm 的 `per_token_group_quant_{fp8,int8}` 都接受任意 group（含 64）。缺的只是 GEMM mainloop。
