# Post-training API and artifact compatibility

This document is the compatibility policy and migration inventory for public post-training surfaces.
It distinguishes Python APIs, configuration, serialized data, and checkpoints because they have
different readers, rollback paths, and retention windows.

The initial `cosmos_framework.posttrain.api` exports are **experimental**. The namespace establishes
one supported import boundary without declaring the exported contracts stable before DPO and GRPO
exercise them end to end. Internal implementation modules remain available as compatibility paths;
they are not deprecated by the initial facade.

A **release train** below means one successful scheduled framework release, not an arbitrary merge
or nightly build. The calendar threshold prevents a fast release cadence from shortening a migration
window; the release threshold keeps compatibility open when no qualifying release occurs.

## Maturity guarantees

| maturity     | compatibility guarantee                                                                                                                                                                                                                                                                                                                                          |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| experimental | The `posttrain.api` namespace remains available, but an exported experimental symbol may change. A rename, signature change, or config change requires a tested compatibility alias or translation for at least one release train or 30 days, whichever is longer, plus a migration note and caller inventory. Persistent writers remain opt-in or shadow-write. |
| beta         | Changes are additive-compatible. A deprecated Python import, call, or config field remains accepted for at least two release trains or 60 days, whichever is longer. It emits one bounded warning per process (rank zero for distributed runs) for the full window. Removal also requires no known in-repo caller and a completed downstream caller audit.       |
| stable       | A stable major contract version has no breaking changes. A breaking change requires a new major version and explicit migration. Prior stable Python/config shims and serialized readers remain supported for at least two release trains or 90 days, whichever is longer, and until retained production artifacts have aged out or been explicitly migrated.     |

## Domain rules

### Python imports and calls

- Compatibility aliases call the same implementation; they do not fork behavior.
- When old and new arguments are supplied with conflicting values, construction fails clearly.
- A removal MR must show that the warning window elapsed, the caller inventory is empty, and old/new
  behavior remained equivalent throughout the window.

### Configuration

- Deprecated fields translate deterministically to the replacement and retain the old default.
- Conflicting old and new fields fail; values are never silently discarded.
- Config migration tests cover serialized resolved configs, not only constructor defaults.

### Record and Manifest documents

- For future schema versions, readers land before writers. Manifest v1 is the historical exception:
  its validation-log serializer already exists, and this change closes the missing reader side.
  New readers accept only explicitly supported versions and reject unknown future major versions.
- Migrations are deterministic and tested. Unknown fields are accepted only within a declared,
  namespaced extension container; unknown top-level fields fail.
- Writers retain a legacy or shadow-write mode until the new format passes its acceptance gate.

### Checkpoints

- Checkpoints are never rewritten in place. The checkpoint manager retains the last committed
  generation as the rollback point.
- New code must read supported prior checkpoint versions before it may write a new one.
- Exact resume and intentional partial migration are distinct, explicit modes.

Other configuration and checkpoint changes must add or update an inventory row before they land.

Each future compatibility change adds or updates one row with its owner, introduction and deprecation
date/version, deadline, warning behavior, known consumers, validating tests, and durable migration
evidence. Removal requires the full warning window, zero known callers, passing compatibility and
old-reader fixtures, and a completed rollback/restore drill.

## Promotion gates

All initial rows remain experimental. Promotion to beta is planned, not implied by this facade.

- **Python data and topology imports:** DPO and GRPO acceptance runs must exercise the public imports,
  the public surface must be construction-complete for their supported recipes, and the caller audit
  and migration inventory must be current.
- **Manifest v1 documents:** representative DPO and GRPO validation logs must pass write/read/bind
  replay, the retained-artifact policy and owner must be recorded, and version rejection plus any
  applicable migration fixtures must remain skip-free in required CI.
