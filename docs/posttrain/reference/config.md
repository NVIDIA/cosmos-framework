# Config system

One posttrain experiment = an **inherited upstream model/data tree** (`defaults`) + a **typed
`rl` section**, in ONE OmegaConf tree. The design serves three stakeholders at once:
researchers keep their existing upstream experiments (inherit them verbatim), infra gets full
CLI override, and every run dumps a resolved YAML that agents/repro tooling can reload.
It is deliberately NOT Hydra-`_target_`-instantiate-everything — typed dataclasses +
LazyConfig inheritance + dotlist override.

## Selecting and overriding

```bash
PYTHONPATH=. torchrun --nproc_per_node=4 --standalone -m cosmos_framework.posttrain.entrypoints.dpo -- \
  experiment=cosmos3_ga_16bm8b_dpo_v1 \
  rl.beta=1000 rl.optimizer.lr=5e-7 rl.max_steps=20 \
  model.config.parallelism.data_parallel_shard_degree=4
```

- `experiment=` selects a registered experiment (Hydra `ConfigStore`).
- ONE dotlist (after `--`) covers **both** halves: RL hypers (`rl.*`, `grid.*`) and the
  inherited model tree (`model.*`) alike.
- Every run writes `<out>/config_resolved.yaml` — fully resolved, reload-able. GRPO attempts add a
  top-level `provenance` mapping to it and a `provenance.<attempt_ts>.json` beside it: the tree hash,
  git commit, interpreter, and job that produced the attempt ([`../guides/grpo.md`](../guides/grpo.md) §7).

`config/build.py` keeps lazy imports, general parallelism resolution, `build_optimizer`, and a thin
explicit backend dispatch. Model-family construction belongs to each `model/*.py`; each algorithm
entry assembles its own stack. `config/config.py` holds the shared
`PosttrainConfig(cosmos3.Config)` base + `build_root` (registration + job/trainer defaults); the
runnable roots are `config/config_dpo.py`, `config/config_grpo.py`, `config/config_ppo.py`,
`config/config_opd.py`, and `config/config_nft.py`.
`PosttrainOPDConfig` inherits `PosttrainGRPOConfig`, preserves its established HF default, and
overrides `algorithm` plus the typed `rl: OPDConfig` field; shared model specs remain on
`PosttrainConfig`.
`PosttrainPPOConfig` adds separate policy/reference/critic model configuration and a `PPOGridConfig`;
the synchronous entry requires Ray, per-role grouping, and a local multi-role checkpoint store.

An online `NativePolicyBuildSpec` names a dotted builder, an explicit `model_id` shared with rollout
and tokenizer shaping, an opaque builder-owned `model_config`, and its data-parallel mesh. Generic
entrypoints read `model_id` but do not require the opaque config to imitate Hugging Face fields or
instantiate it on the driver.

## Adding your own experiment

Drop a file in `config/experiment/dpo/` (auto-registered):

```python
from cosmos_framework.utils.lazy_config import LazyDict
from hydra.core.config_store import ConfigStore
from cosmos_framework.posttrain.config.rl import DPOConfig, OptimizerConfig, PreferenceEnvConfig, RefConfig

my_dpo_exp = LazyDict(dict(
    defaults=["/experiment/cosmos3_ga_16bm8b_v2_midtrain", "_self_"],  # inherit a real upstream experiment
    rl=DPOConfig(
        beta=500.0, max_steps=2000, save_every=250,
        # freeze backbone, train only the OmniMoT gen-pathway params
        optimizer=OptimizerConfig(lr=1e-6, train_keys=["moe_gen", "time_embedder", "vae2llm", "llm2vae"]),
        ref=RefConfig(update_every=0),                       # 0 = frozen DPO anchor
        data=PreferenceEnvConfig(jsonl_path="/path/pref.jsonl", media="video", num_frames=121),
    ),
    job=dict(group="posttrain_dpo", name="my_dpo_exp"),
), flags={"allow_objects": True})
ConfigStore.instance().store(group="experiment", package="_global_", name="my_dpo_exp", node=my_dpo_exp)
```

Then `... entrypoints.dpo -- experiment=my_dpo_exp`. The shipped experiments
(`cosmos3_ga_16bm8b_dpo_v1`, image variant `cosmos3_ga_16bm8b_t2i_dpo_v1`) inherit the 8B
*test* experiment and use in-memory synthetic pairs (`rl.data.synthetic_pairs`), so they run with no external
checkpoint/data.

## Parallelism — two layers, don't mix them

- **Engine mesh** (FSDP/HSDP/CP/CFG-parallel) lives in the inherited
  `model.config.parallelism.*` — how ONE model instance shards.
- **Orchestration** (`grid.*`) is the RL-framework layer above it — who hosts the role
  bodies (`backend`), how roles become `ActorGroup`s (`grouping`), how those groups share or split
  `DeviceGroup`s (`gpu_placement`), and each WG's execution shape.

Use the same names for every role's orchestration shape:

```text
R = *_REPLICAS  # independent WG execution replicas
K = *_RANKS     # worker/process ranks inside each execution replica
```

For policy and rollout this means:

```text
policy  = (POLICY_REPLICAS,  POLICY_RANKS)
rollout = (ROLLOUT_REPLICAS, ROLLOUT_RANKS)

POLICY_REPLICAS = 1
POLICY_RANKS    = dp_replicate * dp_shard  # implemented HSDP-only topology
ROLLOUT_RANKS   = rollout tensor-parallel ranks per engine
```

PPO additionally declares one frozen reference role of width `grid.reference_ranks` and one
trainable critic role of width `grid.critic_ranks`. Their model parallelism is independent of
physical placement; reference and critic retain separate GPU DeviceGroups in both PPO placement
modes.

For the current HSDP-only policy topology, `dp_replicate` and `dp_shard` are the complete Torch
DeviceMesh dimensions inside the policy's `K` ranks. In the Ray backend, each `(R,K)` cell is one
`_Host` actor; local execution has no Ray actor layer.
They are not placement replicas: do not call `dp_replicate` simply "replica", map it to
`grid.num_replicas`, or add framework-owned gradient reduction between policy execution replicas.
FSDP owns gradient synchronization across the policy mesh. Rollout replicas, by contrast, are
independent inference engines, each made of `ROLLOUT_RANKS` ranks.

HF policies configure these dimensions as `model_hf.parallelism.dp_replicate` and
`model_hf.parallelism.dp_shard`. A `NativePolicyBuildSpec` uses the same two field names under
`model.parallelism`; a legacy inherited upstream tree continues to use
`model.config.parallelism.data_parallel_{replicate,shard}_degree`. A concrete native builder may
enforce a narrower contract; Qwen3-VL, for example, accepts pure FSDP only and rejects policy
TP/EP/PP/CP and a replicate axis.

**Per-role shapes (`grid.shapes`).** The fallback policy shape is `(1, ranks)` and the rollout shape
is `(num_replicas, ranks)`.
Set, for example, `grid.shapes = {"policy": [1, 64], "rollout": [16, 4]}` (dotlist:
`grid.shapes.policy=[1,64] grid.shapes.rollout=[16,4]`) to give policy and rollout different
execution shapes. The experience roles (data/rm/replay) derive at `(R_rollout, 1)`. Every axis must
be `>= 1`, and policy `R` must be `1` under the normative contract. Shapes do not allocate GPUs or
select a transport. For online GRPO and OPD, `grid.gpu_placement=colocated` (the default) places
equal-product rollout/experience and policy ActorGroups in one GPU DeviceGroup;
`grid.gpu_placement=disaggregated` assigns separate GPU DeviceGroups. OPD's teacher remains in its
own pool in either case. Both entrypoints use the same lowering and derive `same_gpu` or
`cross_device` from that structure before checking the independent `rl.weight_sync_transport`
choice. By default, unequal policy/rollout products require the Ray disaggregated placement with
`weight_sync_transport="nixl"`. Every policy actor materializes the full bucket; asymmetric routing
assigns each rollout flat actor `q` directly to policy flat actor `q % POLICY_RANKS`.
`weight_sync_r2r_broadcast=true` instead keeps that existing P2R transfer for rollout replica 0 and
then broadcasts the engines' live parameters and persistent buffers between corresponding rollout
ranks over NCCL. The GRPO entry enables exact-byte value verification on its initial sync only;
steady-state sync skips that full-state device-to-host proof. The R2R phase is also independently
callable, with optional verification, after replica 0 loads an eval checkpoint. The OPD entry
currently requires one rollout replica and rejects this option. Wider policy pools retain explicit
idle actors. Ray GPU fractions are private binder details;
there is no fractional topology knob. `grid.gpus_per_role` remains a reserved, unconsumed field.

For an eval-only rollout, bind with `bind_device_groups(..., weight_sync_r2r_broadcast=True)` without
a trainer weight edge, load the desired checkpoint into replica 0, then call
`control.loop.weight_sync.r2r_weight_sync(rollout, model_step=version)`. The same R2R operation and
two-phase version publication used by online relay mode run without a policy role.

Online GRPO/OPD requires explicit `grid.shapes` when `grid.num_replicas > 1`; the legacy scalar no
longer implicitly creates policy execution replicas. This forces policy and rollout widths to be
visible rather than silently choosing an unrunnable same-GPU unequal-product topology.

PPO fields and launch constraints are summarized in [`../guides/ppo.md`](../guides/ppo.md); the
typed source of truth is `config/rl.py::PPOConfig` plus `config/config_ppo.py` validation.

### Shared checkpoint component controls

All training entries use the logical component names `model`, `optimizer`, and `training_state`.
`rl.checkpoint_components` controls cadence and normal-final saves and defaults to the full
`[model, optimizer, training_state]` plan. `rl.validation.checkpoint_components` has the same full
default, but validation does not request a save unless `rl.validation.save_checkpoint=true`; that
switch defaults to `false`. If regular saving and validation coincide, their plans are unioned and
written once.

Only the full plan is exact-resume capable. When a proper subset becomes active as the regular run
plan or for a validation save, the checkpoint manager emits `UserWarning`; a resulting artifact is
committed under the sibling `checkpoint_artifacts/iter_*` namespace without advancing
`latest_checkpoint.txt`. An inactive validation plan does not warn. Empty, duplicate, non-string,
and unknown names are rejected. Emergency saves always override both selections with the full plan.

`rl.keep_optim_last=null` is backend-aware automatic policy: a local primary resolves it to `1`,
while a direct object-store primary resolves it to `0` because remote pruning is unsupported.
Explicit `0` keeps all local optimizer state; another non-negative integer selects that many newest
full iterations. See [`checkpoint.md`](checkpoint.md#logical-component-selection) for physical
component mapping, artifact layout, and resume semantics. No knob controls the `.uploaded` archive
marker that archived checkpoints and artifacts carry; its semantics are described in
[`checkpoint.md`](checkpoint.md#local-checkpoint-archive-upload-rlupload).

Legacy selector migration is explicit: replace `rl.objective=degenerate|clipped` with
`rl.grpo_surrogate=legacy_pg|clipped`, and replace OPD's
`rl.objective_mode=direct|advantage` with `rl.distillation_mode=direct|advantage`. The old keys are
not aliases and fail as unknown keys. `legacy_pg` rejects non-default clipped-only settings rather

Dr-GRPO is a resolved GRPO recipe, not another entry or objective wrapper. Launch
`cosmos_framework.posttrain.entrypoints.grpo` with
`configs/dr_grpo_qwen3b_gsm8k.py`.
The GSM8K recipe records a distinct `algorithm` and job
name, then selects `rl.grpo_surrogate=clipped`, `rl.unbiased_advantage=true`, and
`rl.loss_type=seq-mean-token-sum-fixed`. The shared builder passes the single generation bound from
`rollout.max_tokens` into that reduction and records it in the objective identity; no second
max-response-length field, trainer, placement, or control loop is introduced. See [`objective_customization.md`](../howto/custom-objective.md) for
the general objective contract, entry integration rules, and the Dr-GRPO ownership decision.

The fixed normaliser reduces the gradient scale relative to token-mean reduction.
Choose an optimizer epsilon compatible with that scale and re-tune the learning
rate when changing either the normalizer bound or epsilon.

`rl.optimizer.name=muon` reuses the model stack's `MuonWithAuxAdamW` and shared
`split_orthogonalizable_params` classifier instead of maintaining a posttrain optimizer fork.
Hidden `nn.Linear` weights take the scale-free Newton-Schulz route; embeddings, heads, routers,
norms, biases, convolutions and ambiguous coupled 2-D fusions take auxiliary AdamW. Native
`[experts, rows, cols]` parameters opt into the shared stacked-expert path: an expert-axis FSDP
shard contains complete local matrices, so it avoids gathering every expert on every rank, and
gate/up halves are split before orthogonalisation. Dense sharded matrices still require one BF16
all-gather each. Parameters must be stored in FP32 (`master_dtype=float32`) while FSDP supplies
BF16 compute. `muon_rms_match` sets the initial Moonlight LR scale, not equivalence to an
eps-dominated Adam step; re-tune LR for the objective and response-length regime.

GSPO (Group Sequence Policy Optimization) is a resolved GRPO recipe in the same sense. Launch
`cosmos_framework.posttrain.entrypoints.grpo` with `configs/gspo_qwen3b_gsm8k.py`:

```bash
PYTHONPATH=. python -m cosmos_framework.posttrain.entrypoints.grpo \
  --config cosmos_framework/posttrain/configs/gspo_qwen3b_gsm8k.py
```

The recipe records `algorithm=gspo` with its own job name for provenance and calls
`apply_gspo_knobs`, the one place that turns a clipped `rl` section into the paper's objective:
`rl.grpo_surrogate=clipped`, `rl.importance_sampling_level=sequence`, `rl.lower_bound_ratio=0`,
`rl.epsilon_low=3e-4`, `rl.epsilon_high=4e-4`, `rl.loss_type=seq-mean-token-mean`,
`rl.mini_batch_per_replica=32` (four optimizer steps per 128-trajectory batch), and
`rl.certified_deterministic_forward=true`.

The knob changes one thing inside the clipped surrogate. Instead of one ratio per token, every
loss-masked token of response `i` carries the response ratio `s_i = exp(z_i)`, where `z_i` is the
mean over those tokens of `log π_θ − log π_old`, so the epsilon clip admits or drops whole
responses. `algorithm/primitives/policy_gradient.py::sequence_log_ratio` implements the GSPO-token
form `sg[z_i] + (c_t − sg[c_t])`, whose value, clip decision, and parameter gradient equal the
paper's objective for the one scalar advantage per response that GRPO produces; the log-ratio is
clamped from above at `10` and not from below. Frozen π_old, `temperature`, `logprob_dtype`,
`loss_type`, and the ahead-pass attestation are inherited unchanged. Because the per-token loss is
constant within a response, `seq-mean-token-mean` is the paper's equal-weight mean over responses,
while `token-mean` weights each response by its length.

The response ratio differs from one only when π_old is not the current policy, that is at
`n_mini > 1` (the cached ahead pass) or with `use_rollout_logprobs_for_loss=true`. At `n_mini == 1`
without rollout logprobs every `s_i` is exactly `1`, and the run trains as token-level GRPO in
value and gradient while its identity records GSPO; the config warns. It also warns when the
largest non-negative epsilon exceeds `0.05` and when `logprob_dtype` is not `float32`. These knobs
are honored but leave the sequence clip inert or noisy, so they warn; knobs the sequence-level
loss never reads are rejected instead: `lower_bound_ratio != 0`, `grpo_surrogate=legacy_pg`, OPD,
and per-token (tensor) advantages, which the objective refuses inside its rank-converged prepare
step because one ratio per response means one advantage per response. `min_filter_prefix_tokens`
still applies (the base GSM8K recipe keeps `1`); the response mean runs over exactly the tokens
that stay in the loss.

The clipped objective emits two response-level diagnostics at both levels, weighted by
`train/valid_sequence_count`: `train/seq_clip_frac`, the fraction of responses with at least one
token whose loss the clip changed (all or none of a response at sequence level), and
`train/seq_log_ratio_abs`, the mean over responses of `|z_i|`, the magnitude the sequence clip
compares against `ln(1 ± ε)`. Under `sequence` the token-weighted `train/clip_frac` and
`train/ratio_absdev` become length-weighted response statistics, since a clipped response clips all
of its tokens. The GSPO paper (sec. 5.2) reports a response clip fraction about two orders of
magnitude above GRPO's token clip fraction, so a high `train/seq_clip_frac` is the expected reading
rather than a defect. The objective identity records
`importance_sampling_level` only when it is `sequence`, so existing clipped checkpoints resume
unchanged and a level change refuses exact resume in either direction.

Columns are RENAMED, not projected: `prompt_column` becomes `prompt` and `response_column` becomes
`reference`, and every other column passes through to `obs.representations` for a reward or callback
to read. Those two names are the wiring vocabulary — DataPackers read `prompt`, while a selected
provider declares whether it needs `prompt` and/or `reference` — which keeps rewards and packers
reusable across datasets while config decides which column plays each role.

`data.path` wraps at epoch boundaries. Preflight opens the path only for readability.
Full parsing and materialization happen when the data role is constructed—in its Ray
actor, or in-process for the local backend. Every nonblank JSONL line must be an object.
The configured prompt is either a string or a nonempty conversation list whose items
have a string `role` and a `content` field; a configured response must be present and
non-null. Conversation prompts are rendered through the selected model's chat template
as described in [`datapacker.md`](../howto/custom-datapacker.md). Hub-backed sources are loaded lazily by
the data role; `name`/`subset`/`split` and column mappings apply to training and validation.
Source/reward field compatibility and the limits of that check are documented in
[`validation.md`](../howto/preflight.md). Train-time held-out source, cadence, and sampling
settings are documented separately in [`model_validation.md`](../howto/train-time-validation.md).

Two seeds reach a GRPO run. `rl.seed` orders the prompt source: `data.shuffle` permutes the corpus
with `rl.seed + epoch`, and the arithmetic source draws from `rl.seed`. Top-level `rollout.seed` is
the vLLM engine seed and decides the sampled completions. A "seed replicate" that changes only
`rollout.seed` therefore reads the identical prompt sequence and varies the sampling alone, and a
continuation pool built by removing a file prefix from such a run's data does not remove the rows
the parent consumed, which under a shuffle are a seeded random subset. Preflight warns when
`data.shuffle=true`, `rl.seed=0` and a non-zero `rollout.seed` meet with the flag off ("all arms
share one prompt order"). `rl.data_seed_follows_rollout_seed=true` keys the prompt source on
`rollout.seed`, so one per-arm seed varies both; a per-arm `rl.seed` is the other correct spelling.
`config/rl.py::resolve_data_seed` resolves the value once for preflight and the data role, and the
cursor checkpoint (`roles/env/cursor.py`) records it, so an exact resume refuses a run whose data
seed changed.

Non-finite loss rejection is mandatory and is not disabled by
`optimizer.force_finite_grads=false`. Disabling the gradient check emits an operator
warning and `optim/finite_gradient_check_enabled=0`. Both `DiffusionTrainer` (DPO/NFT) and
`LLMTrainer` (GRPO/OPD plus PPO's policy and critic adapters) use the same reject-without-step
meaning. The shipped DPO, GRPO, PPO, OPD, and NFT control loops fail on the first rejected update;
there is currently no retry or bounded-continuation config.

### Routing replay on a sparse-MoE policy

A sparse MoE's top-k selection over near-tied router scores can vary across
otherwise identical forwards. Routing replay pins the recorded dispatch so
importance ratios and reference scores measure policy changes instead of
routing churn.

`rl.routing_replay=rollout` (Rollout Routing Replay) replays the engine's routing end to end:

- **Rollout.** The vLLM engine is built with `enable_return_routed_experts` (part of the engine
  construction identity) and `VLLMRollout` records `policy_info["rollout_routed_experts"]` next to
  `rollout_logprobs`: the top-k expert ids of every input position of prompt + completion,
  `[P+N-1, layers, top_k]` (the last sampled token is never fed back, so it has no row), kept as
  `uint8` up to 256 experts and narrowed to `int16` beyond. The record is prompt-inclusive on
  purpose: the training forward recomputes the prompt positions and their KV feeds every completion
  logit, so a completion-only pin would leave the prompt's routing churn in place. The layer axis is
  vLLM's text-decoder layer index; the adapter checks its length against its own sparse-block count
  (equal on 30B-A3B, where every layer is sparse) and refuses anything else. An empty completion has
  no record and fails the rollout step loud under `rollout`, where the natural path skips it. The
  codec carries the record as bulk like every large per-token tensor; only its lane-agreement digest
  is inline.
- **Packer.** `shape_policy_input` checks the record against the shaped `input_ids` (the stored
  prompt ids are asserted against the packer's own prefix, so a shifted prefix fails there and a
  wrong row count fails here) and every packer collates it token-aligned into the policy batch as
  `[B, T, layers, top_k]`; the unrecorded last token and the padding hold experts `0..top_k-1`, a
  valid selection whose combine weight is zero on padded rows (`data/packer/forward_routing.py`).
- **Model.** The Qwen3-VL-MoE adapter (`model/protocol.py::ForwardReplayPolicy`) consumes the batch
  key in `prepare_policy_batch` and pins every adapted block; the key never reaches the network.
  This batch-driven pin is the single writer: the ahead pass, the probe and the training forwards of
  a chunk are all pinned because they all prepare the same batch, and no trainer code pins.
- **Trainer.** After every forward it checks that the pinned state matches the knob (refusing a
  replay run whose batches carry no routing and a natural run whose batches pin), applies the MoE
  adapter's relaxed probe tolerance (`0.05` nats on at most 5% of tokens, mesh-wide) only while
  pinned, and reports `train/routing_replay_pinned_tokens` (the rows dispatched through the pin:
  prompt + completion positions, padding excluded when the packer supplies `attention_mask`) and
  `train/routing_replay_pinned_blocks`.

Constraints: the native Qwen3-VL-MoE policy with the vLLM rollout and the clipped surrogate only
(assembly refuses dense and HF backends; `legacy_pg` and OPD refuse the knob at construction, since
neither prepares its batch through the model capability). `rollout` is valid at `n_mini == 1`, where it is the only
mechanism that closes the train/infer routing gap, and pairs naturally with
`use_rollout_logprobs_for_loss=true`, which keeps its own contract: `rollout.temperature ==
rl.temperature == 1.0`, `rollout.top_p=1.0`, `rollout.top_k` disabled and
`rollout.repetition_penalty=1.0` (the engine returns raw, untempered logprobs). The engine-side
capture is incompatible with vLLM pipeline parallelism and KV connectors, neither of which posttrain
uses. An unpinned MoE run (`off`) is held to the same strict probe gate as a dense one.

Normal launch and manifest preflight validate the selected config and required reward
environment-variable names before model allocation. Explicit preflight also instantiates
the model-free dataloader and prepares its first T2V row, catching empty selection,
caption-schema, conditioned-frame, and multi-row-packing failures on that selected path.
It does not scan every row or probe the live reward service. The native video
profile rejects conditioned I2V/V2V inputs and remains T2V-only.

Production v1 requires `grid.backend=ray`, `grid.grouping=single`,
`grid.gpu_placement=colocated`, and uniform `(1, group_size)` shapes for data, rollout,
reward, replay, and policy. The `nft` dispatch profile keeps the control loop free of
topology markers while preserving each exact-rank WFM lane. Future disaggregation must
declare new placement and routing contracts; it does not require a topology branch in
`online_nft_step`.

The release-facing image profile is `cosmos3_nft_t2i_public`; its external
artifact and validation contract is documented in
the [public NFT run guide](../howto/run-posttrain.md#7-nft).

The objective publishes merge-safe `train/optimality_mean` and
`train/optimality_second_moment`. After the trainer's data-parallel reduction,
the entrypoint reconstructs the population standard deviation as
`train/optimality_std`. This avoids averaging a rank-local standard deviation,
which would be zero when each rank owns one sample. Provider diagnostics use
`train/reward_provider/<provider>/<metric>` and carry the configured provider revision
as provenance. Accumulation-window source metrics use `rollout/source_window_rows` and
`rollout/source_committed_rows`.

The experimental 8B recipe bounds its local working set to two iteration directories,
with optimizer state kept only for the newest. The older directory remains
model-loadable but is not a training-resume point. This lower recipe does not configure
an archive destination; production recipes must supply one before treating local
retention as durable publication.

## Bounded video-reward settings

`VideoRewardConfig` binds the rank-local decoded-video adapter described in
[`reward-providers.md`](../howto/custom-reward.md). The model-owned decoder attests finite
`[-1,1]` `[1,3,T,H,W]` output before the adapter sends one uint8 video, FPS, and one
sample identity to the service. Raw scores become
`clamp(fp32(score), reward_clip_min, reward_clip_max) * scale` exactly once.

Service URLs and the bearer token remain actor-environment inputs and never enter
resolved config. Enqueue is not retried because the service exposes no idempotency
key; only correlated result pulls are retryable. Connect/operation timeouts and one
absolute acceptance deadline bound the call. The positional singleton result must be
finite. These contracts make transport failure bounded and attributable; they do not
prove live service availability, cancellation, or reward quality.

`ImageRewardConfig` is an additive specialization of the same bounded transport
and provider-result contract. It requires image conditioning and decoder output
`[1,3,1,H,W]`, serializes CPU uint8 `[1,H,W,3]` with `media_type=image`, and
omits video FPS metadata. The T2V request shape and default remain unchanged.
