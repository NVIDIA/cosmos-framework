# Model and algorithm support

Choose a model **and** a training method before choosing a launcher. Support below includes reusable model/algorithm cores that still need configuration, scripts or data wiring. Concrete recipes are marked separately; missing a recipe does not mean the algorithm is unsupported.

For GR00T customer-demonstration SFT, start with [Isaac-GR00T fine-tuning](https://github.com/NVIDIA/Isaac-GR00T#fine-tuning). Cosmos Framework contains a GR00T-N1.7 supervised action-head implementation, but its public end-to-end GR00T recipe is currently [Joint PPO on LIBERO-Spatial](../posttrain/guides/joint-ppo-gr00t-public.md).

## How to read the tables

The tables distinguish three independent facts:

- **Implementation**: a model adapter and objective exist for the stated training scope. This alone is not a customer-ready launcher.
- **Recipe**: a checked-in configuration or documented command assembles a particular model, data source, runtime and algorithm. A configuration example may still require adaptation.
- **Validation**: the evidence reported by the linked guide, recipe or test. Unit tests, parity tests, short optimizer smokes and measured task evaluations establish different things. A short smoke does not establish convergence or customer-task quality.

The evidence below is recorded in linked code, tests and guides; this page does not report new GPU training runs. Versions, checkpoint revisions, hardware, precision and data contracts remain those of the individual recipe. An unlisted combination is **not established by this table**, rather than implicitly supported or necessarily impossible.

## Support matrix

**Yes** means that the existing model and algorithm cores can be reused, including combinations that still need configuration, a launcher, or data/template/packer wiring. It does not require a standalone recipe or a full training run for every checkpoint. Missing a required model-loading or training-loss capability is not counted as support.

- **Yes*** also counts as supported under this definition, with the connection/runtime work described below.
- **R** links a concrete recipe, configuration example or documented launch. The recipe qualifies its named model/task, not every member of the family; configuration-only examples are identified in the recipe tables below.
- **—** means that the current implementations do not provide this combination; more than ordinary configuration/data wiring is needed.

For **Yes*** HF SFT, the reusable core is the [model-independent CE objective](../../cosmos_framework/posttrain/algorithm/sft.py) plus `LLMTrainer` and a compatible HF logits forward. The [GPT-2 loss/optimizer tests](../../cosmos_framework/posttrain/tests/test_algorithm_sft.py) directly exercise that core outside Qwen. The default conversation-SFT launcher still selects a Qwen-only packer; other families need their own tokenizer/template/media shaping and launcher binding. This wiring gap does not make the underlying SFT algorithm Qwen-only.

For online **Yes*** cells, the HF builder, packer, rollout/teacher and critic must accept the concrete checkpoint and selected runtime. Generic HF VLM online shaping covers text/images, not video; native Qwen3-VL has a separate video packer. GR00T SFT needs an offline source/loop assembled around its existing supervised model/objective. AlpaGym uses its own closed-loop objective; its cell does not claim Dr-GRPO/GSPO support.

The Cosmos3 generator and exported Reasoner are different paths: exporting the Reasoner as Qwen3-VL selects that row, not token-RL support on the diffusion adapter. DPO here is the implemented **Flow-DPO**, not an unimplemented token-DPO for causal LMs.

### Weight transfer and checkpoint boundaries

Online token methods connect the [weight-transfer plane](../../cosmos_framework/posttrain/comm/weight_transfer.py) to rollout. Native Qwen3-VL owns packed-QKV and fused-expert mappings. HF's identity mapper publishes checkpoint-named full tensors; the [vLLM receiver](../../cosmos_framework/posttrain/roles/rollout/vllm_weights.py) calls the engine's own `load_weights` for fusion/sharding. The selected engine must accept that checkpoint format; raw checkpoint names need not equal live packed-parameter names. A loss forward alone does not establish an online integration.

The [checkpoint lifecycle](../../cosmos_framework/posttrain/control/checkpointing.py) saves trainer/model/optimizer and source state per entry point. HF supplies [model export](../../cosmos_framework/posttrain/model/hf.py) with a [small-model round-trip test](../../cosmos_framework/posttrain/tests/test_model_hf_export.py); native SFT uses the [HF materializer](../../cosmos_framework/posttrain/checkpoint/tools/materialize_hf.py). GR00T/π0.5 bind model/processor/simulator identity and have different state scopes. Resume, serving export and cross-repository interchange must be assessed separately.

## GR00T: choosing a repository and handing off a checkpoint

- **Customer demonstrations → SFT → evaluation/deployment:** use [Isaac-GR00T's workflow](https://github.com/NVIDIA/Isaac-GR00T#workflow-overview), including its dataset/modality configuration and policy API. CF's [flow-BC objective](../../cosmos_framework/posttrain/algorithm/flow_bc.py) and [model adapter](../../cosmos_framework/posttrain/model/gr00t/policy.py) are implementation building blocks, not a replacement customer tutorial.
- **Reward/simulator-driven improvement:** use the CF [GR00T Joint PPO guide](../posttrain/guides/joint-ppo-gr00t-public.md) as the documented starting point. Its LIBERO checkpoint and environment are the reference combination; substituting a customer SFT checkpoint requires checking its embodiment, cameras/state, action layout, horizon, processor and normalization statistics against the bound recipe.
- **Return to evaluation/deployment:** CF has a [GR00T checkpoint exporter](../../cosmos_framework/posttrain/scripts/export_gr00t_checkpoint.py) for replacing a matching base checkpoint's action head. It requires exact head keys and shapes. Do not assume it accepts a PPO checkpoint with an added value head: validate that scope and export format before recommending a round trip. Preserve the complete processor/statistics/configuration artifacts and test the exported policy with the intended Isaac-GR00T runtime.

An arbitrary customer **Isaac SFT → CF RL → Isaac deployment** round trip is not qualified by the public LIBERO smoke or the training parity test. This page makes no commitment about future repository consolidation or additional SFT recipes.

## Adding or qualifying another combination

Algorithms bind to [model capability protocols](../../cosmos_framework/posttrain/model/protocol.py), not a universal model allowlist. A compatible architecture is an extension candidate until the required pieces are wired and tested:

1. Bind the model builder and objective capability, including trainable scope and precision. For online training, also bind rollout/scoring, weight transfer and any reference/value model.
2. Supply a model-specific [DataPacker](../posttrain/howto/custom-datapacker.md) or batch collator, plus a compatible [data source](../posttrain/howto/custom-data.md), [reward](../posttrain/howto/custom-reward.md) or [simulator](../posttrain/howto/sim-integration.md) as the algorithm requires.
3. Run configuration/manifest checks and a short training/checkpoint smoke. Record model revision, runtime, topology, dataset and the observed result; use held-out evaluation before claiming quality improvement.

When adding a row, link its implementation or recipe and state the strongest available evidence and remaining limits. Do not copy validation from another model in the same family. See the [extension guide](../posttrain/howto/custom-objective.md) and [preflight limits](../posttrain/howto/preflight.md).
