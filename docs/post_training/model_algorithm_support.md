# Model and algorithm support

Use the matrix to choose a model and training method, then follow a linked recipe or adapt the closest example. **Support and recipe availability are separate:** an existing model/algorithm core counts as supported even when configuration, launch scripts or data wiring still need adaptation.

## Support matrix

- **Yes**: the model adapter and algorithm support this combination.
- **Yes\***: also supported through the existing core, with additional model/data wiring or runtime setup described below.
- **R**: a reference recipe, configuration example or documented launch is available. The recipe sections distinguish these starting points and their scope.
- **—**: the current adapters lack a required capability; configuration or data wiring alone is insufficient. Unlisted combinations may still be adaptable.

Support applies to compatible checkpoints on the selected backend; it does not imply that every checkpoint in a family has been tested. **R** applies to the linked model/task, rather than the whole family.

### Scope and adaptation notes

- **HF SFT:** the default conversation-SFT launcher covers Qwen text (`qwen2`, `qwen2_moe`, `qwen3`, `qwen3_moe`), dense Qwen3.5/3.8 and Qwen3-VL. Other compatible causal decoders and dense VLMs can reuse the CE objective and trainer with a model-specific tokenizer/template, processor, packer and launcher binding. Qwen3-VL-MoE uses the native backend.
- **Online HF methods:** the checkpoint must work with the training backend, rollout/teacher runtime and live-weight loading; PPO also needs a compatible critic. Dense Qwen3.5/3.8 requires a runtime with model support. Generic HF VLM packing covers text and images; native Qwen3-VL has a separate video packer. HF VLM OPD uses the same-token (shared-tokenizer) path; cross-token multimodal OPD uses native Qwen3-VL and currently accepts images.
- **GR00T SFT:** supervised action-head flow matching is implemented, with the backbone frozen. An offline data source and training loop must be assembled around that core; a public end-to-end customer SFT recipe is not provided.
- **Algorithm variants:** native Qwen3-VL GRPO uses the clipped surrogate. Alpamayo's AlpaGym integration provides closed-loop GRPO-like training; its cell does not include Dr-GRPO or GSPO.
- **Diffusion methods:** Flow-DPO is preference optimization for the Cosmos3 flow adapter. DiffusionNFT implements image and video paths; the linked public recipe covers images. GR00T and π0.5 use different action-policy interfaces.
- **Cosmos3 Reasoner:** export as Qwen3-VL and use that row for token-based methods; see [checkpoint conversion](choose_path.md#rl).

## GR00T: choosing a repository and handing off a checkpoint

The repositories currently offer complementary workflows:

1. **Customer demonstrations → SFT:** start with [Isaac-GR00T fine-tuning](https://github.com/NVIDIA/Isaac-GR00T#fine-tuning) for dataset preparation, training, evaluation and deployment. Cosmos Framework also supports supervised action-head training, but does not provide the equivalent end-to-end SFT recipe.
2. **Reward-based improvement:** start with the [Cosmos Framework GR00T Joint PPO guide](../posttrain/guides/joint-ppo-gr00t-public.md). To use a customer SFT checkpoint, match its embodiment, cameras/state, action layout, horizon, processor and normalization statistics to the training and simulator configuration.
3. **Evaluation/deployment after RL:** the [GR00T exporter](../../cosmos_framework/posttrain/scripts/export_gr00t_checkpoint.py) replaces a matching base checkpoint's action head and requires matching keys and shapes. Check compatibility with PPO's added value head before exporting. Preserve processor, statistics and configuration artifacts, then test the policy in the intended Isaac-GR00T runtime.

The public LIBERO recipe demonstrates its named checkpoint/environment combination. A customer SFT → CF RL → deployment handoff needs the compatibility checks above; the recipe does not establish that full round trip for arbitrary checkpoints.

## Adding or qualifying another combination

**Unlisted combinations can often be adapted from existing examples.** Start from the closest **R** example with the same model class and training signal. Compatible models can reuse the objective and trainer while you connect the checkpoint, tokenizer/template, processor and dataset.

| What changes                                                           | Guide / reference                                                                                                                                                                                                                                                                   |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tokenizer/chat template, media inputs or architecture-specific packing | [Custom DataPacker](../posttrain/howto/custom-datapacker.md#adding-a-packer-for-a-new-architecture)                                                                                                                                                                                 |
| Dataset format or a run-local data factory                             | [Custom datasets and DataPackers](../posttrain/howto/custom-data.md)                                                                                                                                                                                                                |
| Loss, reduction or algorithm variant                                   | [Objective customization](../posttrain/howto/custom-objective.md)                                                                                                                                                                                                                   |
| Task scorer or reward service                                          | [Reward providers](../posttrain/howto/custom-reward.md)                                                                                                                                                                                                                             |
| Robot embodiment, observation/action mapping or simulator              | [Simulator integration](../posttrain/howto/sim-integration.md)                                                                                                                                                                                                                      |
| Model forwards, value heads or weight layout                           | [Model capability protocols](../../cosmos_framework/posttrain/model/protocol.py), [model build specification](../../cosmos_framework/posttrain/config/model.py), [extending beyond an objective](../posttrain/howto/custom-objective.md#when-objective-customization-is-not-enough) |

Bind the model and data first. For online methods, also connect rollout/scoring, live-weight transfer and any teacher, reference or value model. Run [preflight checks](../posttrain/howto/preflight.md), then a short training/resume/export smoke before evaluating task quality. If a required model-loading or loss capability is missing, add the corresponding adapter alongside the configuration. A working adaptation can become a new reference recipe.

- **Generic SFT:** the [CE objective](../../cosmos_framework/posttrain/algorithm/sft.py) works with compatible logits and SFT packing, as exercised by the [GPT-2 tests](../../cosmos_framework/posttrain/tests/test_algorithm_sft.py). The default [SFT entry point](../../cosmos_framework/posttrain/entrypoints/sft.py) and [packer builder](../../cosmos_framework/posttrain/data/packer/sft.py) select a narrower set of Qwen families.
- **HF token methods:** [HFModel](../../cosmos_framework/posttrain/model/hf.py) provides causal/image-text forwards and loading. [Packer selection](../../cosmos_framework/posttrain/data/packer/__init__.py), the [HF VLM packer](../../cosmos_framework/posttrain/data/packer/hf_vlm.py) and [GRPO assembly](../../cosmos_framework/posttrain/entrypoints/grpo.py) connect these to common objectives. Generic HF loading rejects MoE VLMs, including `qwen3_5_moe`.
- **Native Qwen3-VL:** [dense policy/value builders](../../cosmos_framework/posttrain/model/qwen3_vl.py), [MoE policy](../../cosmos_framework/posttrain/model/qwen3_vl_moe.py) and [media packing](../../cosmos_framework/posttrain/data/packer/qwen3_vl.py) provide the separate native integration. These builders accept `qwen3_vl` and `qwen3_vl_moe`; packer registration alone does not extend model support.
- **PPO and OPD roles:** [PPO assembly](../../cosmos_framework/posttrain/entrypoints/ppo.py) binds policy, reference and [critic](../../cosmos_framework/posttrain/model/value.py). [OPD assembly](../../cosmos_framework/posttrain/entrypoints/opd.py) and [teacher/objective builders](../../cosmos_framework/posttrain/config/build.py) select teacher modes; DPCA uses the native backend.
- **Diffusion methods:** [DPO](../../cosmos_framework/posttrain/entrypoints/dpo.py) and [NFT](../../cosmos_framework/posttrain/entrypoints/nft.py) assemble the [Cosmos3 flow adapter](../../cosmos_framework/posttrain/model/cosmos3.py). NFT includes video-specific preflight, sampling, decoding and reward wiring.
- **Robot policies:** [GR00T](../../cosmos_framework/posttrain/model/gr00t/policy.py) implements supervised flow matching for [flow-BC](../../cosmos_framework/posttrain/algorithm/flow_bc.py) as well as decision-PPO methods. The current [π0.5 adapter](../../cosmos_framework/posttrain/model/pi05/policy.py) provides decision PPO and lacks the supervised loss/input path; it needs additional implementation for SFT in CF.
- **Online weights and checkpoints:** the [weight-transfer plane](../../cosmos_framework/posttrain/comm/weight_transfer.py) and [vLLM receiver](../../cosmos_framework/posttrain/roles/rollout/vllm_weights.py) must load the selected checkpoint's live tensors. [Checkpoint lifecycle](../../cosmos_framework/posttrain/control/checkpointing.py), [HF export](../../cosmos_framework/posttrain/model/hf.py) and [native SFT materialization](../../cosmos_framework/posttrain/checkpoint/tools/materialize_hf.py) cover different save/export paths; training resume and deployment export have distinct formats.
